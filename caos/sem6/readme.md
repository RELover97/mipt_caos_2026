# Как программа работает с памятью в Linux на архитектуре x86-64

Рассмотрим задачи обхода элементов массива и элементов односвязного списка. Сложность у обоих алгоритмов — `O(n)`. Но реальное время выполнения может различаться в десятки раз. Разберёмся, как связаны указатели, кэш процессора, страницы памяти, `malloc`, `mmap` и работа Linux с оперативной памятью.

## 1. Сборка и запуск

```bash
cmake -S . -B build -DCMAKE_BUILD_TYPE=Release
cmake --build build -j
```

Запуск:

```bash
./build/01_locality 100000
./build/02_mmap
```


`02_mmap` ждёт нажатия Enter: в этот момент мы сможем посмотреть адресное пространство программы из другого терминала.

Мы собираем в `Release`, чтобы компилятор оптимизировал циклы.

## 2. Почему массив часто быстрее списка?

**Файл:** `src/01_locality.c`

Главные циклы выглядят так:

```c
for (int i = 0; i < n; ++i)
    sum_array += values[i];

for (Node *p = head; p != NULL; p = p->next)
    sum_list += p->value;
```

Массив хранит элементы подряд. Это удобно для процессора: память читается не по одному байту, а порциями — **кэш-линиями** (на многих x86-64 процессорах это 64 байта). Подгрузив одну линию, процессор может получить сразу несколько элементов массива. Следующие адреса легко предсказать, поэтому помогает и аппаратная предвыборка (*prefetching*).

У связного списка следующий адрес находится в поле `next`. Прежде чем узнать следующий адрес, надо прочитать текущий узел. Если узлы разбросаны по памяти, переходы становятся зависимыми друг от друга и часто приводят к промахам кэша (*cache misses*).

В нашей программе узлы физически размещены в **одном массиве `Node`**, но мы случайно перемешиваем порядок указателей `next`. Для измерения используются четыре повтора каждого обхода; время создания структур не учитывается.

У процессора обычно есть несколько уровней кэша: L1, L2, L3. Чем ближе уровень к ядру, тем он обычно меньше и быстрее. Информация, которой нет в нужном кэше, ищется дальше, вплоть до RAM.

Пробуем разные размеры массива и списка:

```bash
./build/01_locality 10000
./build/01_locality 100000
./build/01_locality 1000000
```

Можно узнать сведения о кэше установленного процессора:

```bash
lscpu -C
```

## 3. Виртуальные адреса, страницы и TLB

В работающей программе указатели содержат **виртуальные адреса**. Процессор переводит их в физические адреса с помощью таблиц страниц, которыми управляет ОС. В Linux x86-64 базовая страница часто равна **4 КиБ**; проверить можно так:

```bash
getconf PAGESIZE
```

Адрес можно условно представить следующим образом: старшие биты содержат номер виртуальной страницы, младшие - смещение внутри страницы. 

Для страницы 4096 байт смещение занимает 12 бит. На x86-64 таблицы обычно многоуровневые: каждая таблица из 512 восьмибайтовых записей помещается в страницу размером 4 КиБ. Такой подход не требует выделять огромную плоскую таблицу под всё потенциальное адресное пространство.

Чтобы не читать таблицы страниц при каждом обращении, процессор кэширует результаты трансляции в **TLB** (*Translation Lookaside Buffer*).

Важно различать три разных ситуации:

| Событие | Что это означает |
| --- | --- |
| Cache miss | В выбранном уровне кэша CPU не оказалось нужной кэш-линии данных |
| TLB miss | В TLB нет готового перевода виртуального адреса; процессор может обойти таблицы страниц самостоятельно |
| Page fault | Доступ нельзя завершить по текущим записям таблиц страниц; управление получает ядро ОС |

**Page fault — не обязательно ошибка.** Он может быть совершенно обычной частью работы программы.

## 4. `mmap`: выделили адреса, но не обязательно RAM

**Файл:** `src/02_mmap.c`

Вместо `malloc` напрямую попросим у Linux область виртуальных адресов:

```c
void *region = mmap(NULL, bytes, PROT_READ | PROT_WRITE,
                    MAP_PRIVATE | MAP_ANONYMOUS, -1, 0);
```

`NULL` означает, что адрес выберет ядро. `PROT_READ | PROT_WRITE` разрешает чтение и запись. `MAP_ANONYMOUS` создаёт отображение без файла, `MAP_PRIVATE` — частное отображение.

Программа печатает данные **до `mmap`**, **после `mmap`** и **после записи в начало каждой страницы**. Она читает `/proc/self/status`:

- `VmSize` — размер виртуального адресного пространства, занятого отображениями;
- `VmRSS` — приблизительный размер страниц, находящихся в физической RAM (*resident set size*).

Обычно `VmSize` увеличится сразу, а `VmRSS` заметно вырастет только после первого обращения на запись к страницам. Это **demand paging**: физическая память для анонимных страниц выдаётся тогда, когда действительно понадобится. При нехватке ресурсов поведение может отличаться.

Счётчики обращений к обработчику page fault программа получает через `getrusage`:

- **Minor page fault** — страницу удалось подготовить без ожидания чтения самой страницы с внешнего хранилища; пример — выделение нулевой анонимной страницы.
- **Major page fault** — разрешение page fault потребовало ожидания ввода-вывода страницы из хранилища (диска); в случае анонимного отображения, обычно, не встречается.

После первой записи к страницам ожидаются преимущественно minor faults. Повторное чтение обычно уже не вызывает новых page faults.

Виды флагов `mmap`:

- `MAP_PRIVATE` — изменения не записываются в исходный файл; для файловых отображений применяется copy-on-write.

- `MAP_SHARED` — изменения отображения видны другим отображениям той же области и могут записываться обратно в файл.

- `MAP_ANONYMOUS` — отображение не связано с файлом и первоначально заполнено нулями.

- `MAP_FIXED` — использовать именно указанный адрес, заменяя пересекающиеся отображения. Опасный флаг, для обычных задач не нужен.

### Как посмотреть отображения из терминала

Запусти `./build/02_mmap` и остановись на приглашении `Press Enter to unmap...`. Программа напечатает свой PID, например `12345`. Во втором терминале выполни:

```bash
cat /proc/12345/maps
cat /proc/12345/status | grep -E 'VmSize|VmRSS'
```

Файл `maps` показывает диапазоны виртуальных адресов, права доступа и связанные с ними файлы. Найди диапазон, содержащий напечатанный адрес `region`. Обозначение `rw-p` означает чтение, запись и *private mapping*. Ядро может объединять соседние отображения, поэтому границы в `maps` не всегда совпадают с отдельным вызовом `mmap`.

`/proc/self/maps` относится к **тому экземпляру программы, который читает файл**. Команда `cat /proc/self/maps` покажет адресное пространство `cat`, а не другого процесса.

## 5. Как работает выделение памяти

**Файлы:** `src/03_bump.c` и `src/04_buckets.c`

При каждом `malloc` библиотека необязательно обращается к ядру. Часто аллокатор получает большой участок памяти, а затем сам раздаёт блоки нужного размера. Для получения памяти применяются в том числе `brk` и `mmap`.

### `brk`, `sbrk` и граница heap

Исторически `brk` изменяет границу области данных процесса, называемую *program break*. `sbrk` — интерфейс для работы с этой границей (сегодня устаревший и не рекомендуемый для новых аллокаторов). В `03_bump.c` мы вызываем **только `sbrk(0)`**, чтобы увидеть текущий program break. Управление памятью нашего учебного аллокатора реализовано через `mmap`; мы не вмешиваемся в работу системного `malloc`.

### Bump allocator

Первый аллокатор хранит два значения: начало памяти `memory` и количество уже использованных байт `used`. Для выдачи новой памяти:

1. округляет очередной адрес с учётом выравнивания;
2. проверяет, что хватает места;
3. возвращает адрес и передвигает `used`.

Аллокатор очень быстрый, но не умеет вернуть один отдельный блок. Можно лишь сбросить всю арену сразу (`used = 0`) — после этого старые указатели больше использовать нельзя, даже если их адреса совпадают с новыми.

```bash
./build/03_bump
```

### Free lists и корзины размеров

Во втором варианте появляются **корзины** (*size buckets*) на 16, 32, 64, 128 байт и **списки свободных блоков** (*free lists*). Запрос 24 байт попадает в корзину 32, а запрос 80 байт — в корзину 128.

Когда мы возвращаем 32-байтный блок, он попадает в свободный список этой корзины. Запрос 20 байт может получить тот же адрес:

```bash
./build/04_buckets
```

Интересная деталь: внутри свободного блока мы храним указатель на следующий свободный блок (`FreeBlock *next`). Это и есть свободный односвязный список.

Из-за округления размеров появляется **внутренняя фрагментация**: при запросе 24 байт мы выдаём 32, то есть 8 байт остаются неиспользованными. Также бывает**внешняя фрагментация** — когда свободная память разбита на множество разрозненных участков.

Это учебный аллокатор, не аналог `malloc`. При возврате блока вызывающая сторона обязана указать правильный размерный класс. Мы не проверяем двойное освобождение, чужие указатели и многие другие ошибки.

**Вопрос:** если мы вернули блок во free list, почему RSS программы может не уменьшиться? Потому что вернуть блок аллокатору — не то же самое, что отдать физическую страницу ОС.

## 6. Как программа размещена в памяти: ELF и `readelf`

Скомпилированная программа в Linux обычно хранится в файле формата **ELF**. В нём содержатся код, данные и описание того, какие области загрузчик должен отобразить в память.

Посмотрите секции и сегменты программы:

```bash
readelf -SW ./build/01_locality
readelf -lW ./build/01_locality
```

Обратите внимание на `.text` (машинный код), `.rodata` (константные данные), `.data` (инициализированные изменяемые глобальные переменные) и `.bss` (нулевые/неинициализированные глобальные и статические объекты). Секции — понятие формата и компоновки ELF; во время загрузки важны также **сегменты `LOAD`**, которые могут объединять несколько секций.

Сравните их с `/proc/<PID>/maps`, когда `02_mmap` остановлена. У выполняющейся программы есть также стек, анонимные отображения, библиотеки и часто область `[heap]`, управляемая через `brk`. Реальные адреса могут изменяться между запусками из-за **ASLR** (**address space layout randomization** — **рандомизация размещения адресного пространства** - технология, применяемая в операционных системах, при использовании которой случайным образом изменяется расположение в адресном пространстве процесса важных структур данных, а именно образов исполняемого файла, подгружаемых библиотек, кучи и стека). Сырые значения из `readelf` не всегда прямо совпадают с адресами в `maps`, например у PIE-программы они смещаются на базу загрузки (**Position-Independent Executable** - **Позиционно-независимый исполняемый файл** - может быть загружен по произвольному адресу в память).

**Вопрос:** где находится память, выданная нашим `mmap`-аллокатором: в `.bss`, `[heap]` или в отдельном анонимном отображении? (Правильное место — анонимное отображение; оно может отображаться без собственного имени.)

## 7. Файловый `mmap`, `ftruncate` и writeback

**Файл:** `src/05_filemap.c`

`mmap` может отображать не только анонимную память, но и содержимое файла. Мы создаём временный файл, делаем его размером в три страницы:

```c
ftruncate(fd, 3 * page);
```

`ftruncate` изменяет размер файла через открытый файловый дескриптор. Родственная функция `truncate(path, size)` работает по имени пути. Увеличение файла создаёт логические нулевые байты (не обязательно немедленно выделяя место на диске).

Затем отображаем файл с флагом `MAP_SHARED`. Запись `shared[0] = 'A'` становится видимой при чтении файла через `pread` и другим согласованным отображениям, но **видимость не гарантирует, что данные уже физически сброшены на носитель**. Для явного запроса синхронизации используем `msync(..., MS_SYNC)`; `fsync(fd)` синхронизирует содержимое и необходимую метаинформацию файла.

Второе отображение открываем с `MAP_PRIVATE`. Запись `private_data[0] = 'P'` не изменяет исходный файл: для изменённой страницы применяется **copy-on-write (COW)**.

В конце программа уменьшает размер файла с трёх страниц до одной. Мы **специально не обращаемся** после этого к страницам с номером 2 и 3: такой доступ к целым страницам за новым концом файла может вызвать `SIGBUS`.

```bash
./build/05_filemap
```

Обратите внимание: при файловом `mmap` major page faults могут появляться, но их точное число зависит от page cache, файловой системы и состояния машины. Не стоит ожидать строго фиксированное количество.

### Что такое page cache и writeback?

Linux использует свободную оперативную память в том числе для **page cache** — кэширования содержимого файлов. Поэтому чтение файла необязательно означает чтение с накопителя. Изменённые файловые страницы называют *dirty pages*. Ядро может записывать их на носитель позднее — это **writeback**. Синхронизация `msync`/`fsync` позволяет явно потребовать соответствующего сброса.

## 8. Memory reclaim и OOM killer

**Файл:** `src/06_reclaim.c`

Оперативная память ограничена. Если свободной памяти становится мало, Linux пытается вернуть страницы для других нужд — выполнить **memory reclaim**.

В качестве безопасной демонстрации сначала запишем по одному байту в 32 МиБ анонимных страниц, а затем вызовем:

```c
madvise(region, bytes, MADV_DONTNEED);
```

Это **явная подсказка приложения**, а не автоматический reclaim под давлением памяти. Для такого частного анонимного отображения Linux может отбросить содержимое страниц. Повторное чтение вернёт нули и вызовет новые minor page faults. При этом RSS после чтений может **не вырасти**: ядро может показывать всем чтениям одну общую нулевую страницу. Чтобы снова получить собственные физические страницы, нужно записать данные.

```bash
./build/06_reclaim
```

При нехватке памяти ядро может освобождать чистые файловые страницы из page cache, записывать грязные страницы (writeback), а при наличии swap — вытеснять подходящие анонимные страницы на swap-носитель. Процесс может испытывать заметные задержки на такой работе. Если освободить память не удаётся, возможна работа **OOM killer** (*Out Of Memory killer*), который выбирает задачу для завершения. OOM может возникнуть и из-за лимита памяти контейнера, даже если в системе ещё есть свободная RAM.

**Не пытайтесь специально вызвать OOM на общей машине.** Это может завершить несохранённые программы и нарушить работу системы. В нашем примере OOM только обсуждается, но не провоцируется.

Полезные команды наблюдения:

```bash
cat /proc/meminfo | head -25     # память всей системы
cat /proc/self/status | grep -E 'VmSize|VmRSS'
vmstat 1 5                      # сводная статистика по памяти и swap
cat /proc/pressure/memory      # если PSI поддерживается ядром
```

Файла `/proc/mem` в стандартном Linux для этой задачи нет: нужен **`/proc/meminfo`**. В `meminfo` смотрите прежде всего `MemTotal`, `MemAvailable`, `Cached`, `Dirty`, `Writeback`, `SwapTotal` и `SwapFree`. Показатель `MemFree` не равен всей памяти, которую система способна быстро предоставить приложению: часть RAM занята полезным кэшем.

## Что стоит вынести из этой работы

- Сложность `O(n)` не рассказывает нам о задержках доступа к памяти. Локальность данных имеет значение.
- `mmap` работает с **виртуальным адресным пространством**, а физические страницы часто предоставляются лениво.
- Cache miss, TLB miss и page fault — три **разных** механизма.
- Аллокатор обычно переиспользует память внутри приложения; `free` не гарантирует немедленного уменьшения RSS.
- `MAP_SHARED` и `MAP_PRIVATE` по-разному работают с изменениями файла; dirty-страницы требуют writeback.
- Linux использует свободную память под кэш, возвращает страницы при необходимости и только в тяжёлых ситуациях может прибегать к OOM killer.

### Важно

Код намеренно учебный. В нескольких местах опущены дополнительные проверки и универсальная обработка ошибок ради понятности основных механизмов. Для production-кода потребуются более строгие проверки границ, времени жизни указателей и состояний аллокатора. Не используйте примеры с `mmap` и `sbrk` как готовую замену стандартному `malloc`.
